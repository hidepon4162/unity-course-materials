## Git運用ルール <a id="git-rules"></a>

> 採用担当者はcommit履歴も確認します。質の高いcommitを意識してください。

**commitメッセージの書き方**

```
feat: プレイヤーの移動処理を実装（Rigidbody使用）
fix: NullReferenceException を修正（PlayerController の null チェック追加）
refactor: EnemyController をコンポーネント分割
docs: README に操作方法を追記
```

| ❌ 避けるべき例 | ✅ 良い例 |
|----------------|-----------|
| 修正 / あ / 完成版 | fix: 当たり判定のズレを修正 |
| いろいろ / test | feat: タイトル画面にフェードイン追加 |

**基本ルール**

- **作業した日は必ずcommitする**（毎日でなくてもよいが、作業日には残す）
- **1commitに1つの意味**（機能追加とバグ修正を同じcommitにまとめない）
- 1日 2〜3回 Push を目安に
- 作業前に必ず **Pull** して最新を取得
- `.gitignore` は Unity 公式テンプレートを使用

**ブランチ（任意）**

新機能追加時はブランチを切る習慣をつけると、実務感が伝わります。

```
ブランチ名の例：feature/enemy-ai、fix/null-check
```

**フォルダ構成（推奨）**

```
Assets/
├─ Scripts/
├─ Prefabs/
├─ Scenes/
├─ UI/
└─ Audio/
```

## 就活前チェックリスト <a id="job-hunting-checklist"></a>

> 就活でGitHubを提出する際に確認してください。詳細は [就活に向けたGitHubポートフォリオ整備ガイド](https://soft-rime.com/post-28642/) を参照。

### README

- [ ] 概要（何を・なぜ作ったか）が1〜2文で書いてある
- [ ] 使用技術が列挙されている

### Git

- [ ] 制作期間中、複数の日付にわたってcommitがある
- [ ] commitメッセージが内容を表している（`feat:` `fix:` など）
- [ ] commitが最終日だけに集中していない

### 全体

- [ ] リポジトリが **public** になっている
- [ ] ビルド済みexeが **Releases** に登録されている
- [ ] 説明なしに他者が見て内容が伝わるか確認した
